# 詳細仕様: 問い合わせフォームURL 自動収集ツール

## 1. 対象データ
- スプレッドシートID: `1J748-Kt8OOxlOh6iEfLv6Viya9nuzBB1xVsZ38jZdS0`
- シート名: `整形済み_診断サイト受託`
- 列インデックス（1始まり / A=1）:
  - E(5)=会社名, F(6)=店舗名/サービス名, **G(7)=公式URL**, **H(8)=問い合わせフォームURL**,
    I(9)=メールアドレス, J(10)=電話番号, **N(14)=対応日**

## 2. 抽出条件（この行だけ処理）
- `G(公式URL)` が非空
- `H(問い合わせフォームURL)` が空
- `N(対応日)` が空
- ※ H に既存値がある行、N に値がある行は**読み飛ばす（上書き禁止）**

## 3. 重複回避
- `baseline_results.csv`（列: 行番号, 会社名, 公式URL, 問い合わせフォームURL, 備考）を起動時に読む。
- 同一行番号、または同一の公式URL文字列がbaselineにあれば、その結果を採用し**再調査しない**。
  - baselineの `問い合わせフォームURL` が空 = 過去に「特定できず」なので **「ー」** を書き込む。
- 実行ごとに、その回の結果を `run_log_YYYYMMDD.csv` として追記保存。

## 4. フォーム発見アルゴリズム
入力: 公式URL（無ければ会社名）。出力: フォームURL or 空（=見つからず→「ー」）。

### 4-1. モール店URLの判定（最優先）
公式URLのホストが以下を含む場合は「モール店」とみなす:
`rakuten.co.jp`, `rakuten.ne.jp`, `store.shopping.yahoo.co.jp`, `shopping.geocities.jp`,
`amazon.co.jp`, `qoo10.jp`, `mercari`, `paypaymall`, `wowma`
- モール店は独立した問い合わせフォームを持たないことが多い（連絡はモールのログイン必須メッセージ機能経由）。
- 対応: **会社名/店舗名から運営会社の自社サイトを検索**（4-3）。自社サイトが見つかればそのフォームを探す。
  見つからなければ **空（→「ー」）** とし、備考に「モール店・独立フォームなし（運営: 会社名 / メール / TEL）」を残す。

### 4-2. 独自ドメインのサイト内探索
1. 公式URLのHTMLを取得（タイムアウト15s、UA例: `Mozilla/5.0 (compatible; ContactFinder/1.0)`、間隔1〜2s）。
2. ページ内の `<a href>` を収集し、リンクテキスト/URLを次のキーワードでスコアリング（大文字小文字・全半角無視）:
   - 高: `お問い合わせ`, `お問合せ`, `問い合わせ`, `問合せ`, `contact`, `inquiry`, `otoiawase`, `toiawase`
   - 中: `お客様`, `ご相談`, `support`, `form`, `mail`
   - 除外: `recruit`, `採用`, `ir`, `privacy`, `login`（用途違いは減点。ただし他に候補が無ければ許容）
3. 最高スコアのリンクへ遷移（相対URLは絶対化）。遷移先に
   `<form>` 要素、または `input[type=email]/textarea`、または `mailto:` があれば**フォームページと判定**して採用。
4. トップに無ければ `/contact`, `/contact/`, `/inquiry/`, `/otoiawase/`, `/contact-us/` 等の
   慣用パスを直接試す（HEAD/GETで200を確認）。
5. 法人向け・個人向けが分かれるサイトは**用途に合う方（企業/取引/一般）を主**に採用し、
   もう一方や電話/メールは備考へ。

### 4-3. 会社名からの検索（サイト未知・モール店の運営会社特定）
- 検索APIを利用（下記いずれか。APIキーは環境変数）:
  - Google Programmable Search (Custom Search JSON API): `GOOGLE_CSE_ID`, `GOOGLE_API_KEY`
  - もしくは SerpAPI: `SERPAPI_KEY`、Bing Search: `BING_API_KEY`
- クエリ例: `"<会社名>" お問い合わせ` / `"<店舗名>" 運営会社 お問い合わせ` / `<domain> contact`
- 上位結果から自社ドメインの `contact/inquiry` ページを推定し、4-2で検証。
- **検索APIが使えない環境の場合**は、モール店・サイト未知の行はスキップ（=「ー」）とし、READMEにその旨明記。

### 4-4. 出力の確定
- フォームURLが確定 → そのURL。
- 確定できず → 空 → **H列には「ー」** を書き込む。
- どちらの場合も判定理由・代替連絡先(メール/TEL)をログの備考に残す。

## 5. 書き込み（H列）
- `gspread` の `worksheet.update_cell(row, 8, value)` もしくは batch update。
- **書き込み前に必ず現在のH値を再取得**し、空のときのみ書き込む（多重実行・手動編集との競合防止）。
- API制限対策: バッチ更新（例 50件ごと）＋指数バックオフ。1回の実行で処理する最大件数は環境変数で上限設定可（例 `MAX_ROWS_PER_RUN=200`）。

## 6. スケジューリング（毎日12:00 JST）
以下から1つ実装（推奨順）:
1. **GitHub Actions**: `on: schedule: - cron: "0 3 * * *"`（UTC 03:00 = JST 12:00）。SA鍵とAPIキーはRepository Secretsに格納。
2. **サーバのcron**: `0 12 * * *`（サーバのTZをJSTに）。
3. **Google Cloud Scheduler + Cloud Run/Functions**: 12:00 JSTで起動。
※ cronはUTC基準のものが多い点に注意（JST12:00 = UTC03:00）。

## 7. 認証・事前準備（READMEに書く）
1. GCPでプロジェクト作成 → Google Sheets API 有効化。
2. サービスアカウント作成 → JSON鍵をダウンロード（`GOOGLE_APPLICATION_CREDENTIALS` で参照）。
3. **対象スプレッドシートを、サービスアカウントのメールアドレス（xxx@xxx.iam.gserviceaccount.com）に「編集者」で共有**。
4. 検索APIを使う場合はそのキーも取得。

## 8. 受入基準（Definition of Done）
- 抽出条件に一致する行だけが処理され、既存H値・N値ありの行は不変。
- 見つかった行はフォームURL、見つからない行は「ー」がH列に入る。
- baselineの392件は再調査されず結果が流用される。
- 毎日12:00 JSTに自動実行される設定が動作する。
- 実行ログ（行番号・会社名・結果・理由）が残る。
- 途中失敗しても再実行で重複なく続行できる（冪等）。
- README通りにセットアップすれば第三者が再現実行できる。

## 9. 参考（今回の調査で得た実データの傾向）
- 対象は全体で約392件。うち**フォームURL特定 244件 / 特定できず(モール店中心) 148件**。
- モール店（特に楽天）は独立フォーム無しが大半 → 「ー」。運営会社の自社サイトがある場合のみフォーム取得可。
- 大手（ニトリ/無印/コクヨ/帝人/カゴメ 等）や独自ドメイン企業・自治体・学校は `/contact` `/inquiry` 系フォームが概ね存在。
- baseline_results.csv の「備考」に、フォーム無し行のメール/TEL・注意点（同名企業の取り違え注意 等）を記載済み。
